## 3. Yjs / WebSocket collaboration

- `HandleWikiWebSocket` (wiki_ws_handlers.go:53):
  - It takes the user from the request context, falling back to a `?token=` JWT (:57-76).
  - It takes the page from `?page_id=` (:79).
  - Authorization is a **single project-membership check at connect time** (:106). Nothing is re-checked per message or when access is revoked.
  - `CheckOrigin` always returns true (:25).
- Message handling:
  - `sync_request` (:211) reads all `yjs_updates` for `client.PageID`.
  - `update` (:262) writes to `yjs_updates` and broadcasts to the room `page:&lt;id&gt;`.
  - `awareness` messages are broadcast without being stored.
  - The room manager is `api/internal/collab/manager.go`.
- **In practice this path is dead:**
  - The route sits inside `JWTAuth`, which requires an `Authorization` header, so the `?token=` fallback is never reached.
  - The frontend (`web/src/components/WikiEditor.tsx:1255`) uses y-websocket at `/api/wiki/collab/wiki-page-{id}?token=`. That path doesn't match the route, and it sends no `page_id`.
  - y-websocket's binary protocol doesn't match the server's JSON messages either.
  - Real saves go through PUT `/content`. Still, add the visibility check here too.
- The Yjs processor (`api/internal/yjs-processor/index.js`, Express `/apply-updates` and `/extract-blocks`) is stateless and has no database access. It is called only from `api/internal/yjs/client.go`, which the indexing and snapshot workers use.

## 7. Is there a central access helper?

**No.** There are three near-identical helpers, and they're only partly used:
- `checkWikiPageAccess` (wiki_annotation_handlers.go:58): used by annotations only.
- `fetchWikiPageWithAccess` (wiki_download_handler.go:479): used by PDF and Markdown only.
- The wiki_handlers.go handlers each inline "load page, then `checkProjectAccess`".
- There is also `userHasProjectAccess` (project_settings_handlers.go:531, owner or member), which wiki doesn't use.

**Suggested chokepoints**
1. **Single-page reads and writes.** Create one `s.authorizeWikiPage(ctx, userID, pageID, needWrite) (*ent.WikiPage, error)` that does membership plus the visibility / allow-list check. Replace these calls with it:
   - wiki_handlers.go :295, :342, :480, :540, :807, :879, :962, :1146
   - `checkWikiPageAccess` and `fetchWikiPageWithAccess`
   - wiki_ws_handlers.go:106
   - watcher_handlers.go:161, :211
   - cloudinary_handlers.go :434, :1143, :1188
   - the two annotation-comment handlers, which should resolve their page
2. **List and search reads.** Create one SQL / Ent predicate, e.g. `visibleWikiPagesPredicate(userID)` / `wikiVisibilitySQL("wp", userID)`, to AND into:
   - `HandleListWikiPages` :109 and :127
   - `searchWikiBlocks`, `searchWikiFTS`, `searchWikiSemantic`, `searchWikiHybrid` (all join `wiki_pages wp`)
   - `HandleAutocompletePages` :556
   - `searchWikiSQLite` / `searchWikiPostgres` (search_handlers.go:349, :390)
   - `fetchUserActivity`'s four wiki queries
   - `HandleListImages` wiki union :836, :857
   - `HandleGetProjectGraph` :207 (filter `entity_type='wiki'` nodes, and their edges)

   Fixing `getUserAccessibleProjects` alone is not enough, because visibility is per page.
3. **Side channels:**
   - Make `extractMentionedUserIDs` / notifications respect the allow-list.
   - Make `syncGraphLinks` skip or redact targets the editor can't see.
   - Tie the PDF job to its user/page.
   - Decide whether child pages inherit a protected parent's visibility (`loadWikiTree` in wiki_hierarchy.go:65 is where to handle that).
4. **Public links** need a new unauthenticated route (e.g. `/public/wiki/{token}`) registered in the public section of main.go (~:233-435). It should reuse the render path in `wiki_preview_handler.go`, and account for go-draw embeds and Cloudinary URLs.
5. **Tests.** Add the new routes to `buildTestRouter` and `openapi.yaml`, since today neither has any wiki routes.
